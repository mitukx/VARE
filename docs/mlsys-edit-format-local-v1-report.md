# Local MLX proposal campaign: edit-format apply path v1

**Result: no model proposal was correct; the scripted control did not produce a measurable speedup.** This is a negative local-model engineering result on a public task, not evidence of model capability improvement.

## Question and protocol

Can a real local model propose a behavior-preserving optimization to VARE's rollout edit-apply path, and can an independent evaluator establish both correctness and a measurable latency benefit?

The target was `src/vare/learning_pipeline/edit_format.py::_relaxed_replace`. The task allowed edits only to that function and required the same output for all inputs. The frozen measurement protocol is [`mlsys_edit_format_local_benchmark_v1.json`](../protocols/mlsys_edit_format_local_benchmark_v1.json), SHA-256 `53a9914324d60a1b553b9b7921d3c4727053bab8874c4f17e935133392eed8d1`. It set the performance acceptance rule before the successful scripted-control timing run: the A/A 95% interval must contain zero, the lower 95% interval for geometric-mean speedup must exceed 1, and point speedup must be at least 1.05. The proposals had already been generated by then; the protocol records that ordering.

The proposer saw the target module, task statement, and seven public behavioral cases. It did not see the scripted control patch, generated differential inputs, expected outputs, or reserved data. The trusted parent computed expected outputs from the unchanged baseline. Each candidate ran through `vare.isolated_candidate.grade_calls` in a digest-pinned Colima container with network disabled, read-only root, dropped capabilities, no-new-privileges, and an unprivileged UID. This demonstrates the declared narrow interface only; it is not a claim that arbitrary repository pytest suites are secure in this way.

## Real model attempts

The model was `mlx-community/Qwen3-4B-Instruct-2507-4bit`, local snapshot revision `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b`, run on an M1 Pro with 32 GiB unified memory using Python 3.12.12, MLX 0.32.4, and MLX-LM 0.32.2. Both generations were offline. The two prompts, complete responses, metadata, first candidate source, and evaluator result are retained under [`results/mlsys-edit-format-local-v1/proposals/`](../results/mlsys-edit-format-local-v1/proposals/).

| Attempt | Prompt / completion tokens | Generation time | Output | Independent result |
| --- | ---: | ---: | --- | --- |
| 1 | 2,042 / 320 | 12.070 s (53.14 tok/s) | Regex-based first-match rewrite | 25/31; rejected |
| 2 | 2,479 / 331 | 15.533 s (51.08 tok/s) | Same function AST as attempt 1, with comment-only differences | Rejected as duplicate; no redundant rerun |

Attempt 1 failed the public trailing-whitespace case and five of 24 generated differential cases. It found the first matching span rather than preserving the original unique-match and line-boundary behavior. Attempt 2 received only aggregate failure counts, not failing inputs or expected outputs, but repeated the same implementation. The campaign produced two syntactically valid proposals, one unique candidate, zero correct candidates, and zero independently accepted changes. Neither proposal was timed.

The functional controls behaved as intended: unchanged baseline **31/31**, the scripted PR-173 known-good patch **31/31**, and a deliberately incorrect control **21/31** (10 detected failures). These controls show that the evaluator distinguished this known behavior-preserving control from a simple broken implementation on this case set. They do not estimate general false-acceptance or false-rejection rates.

## Scripted-control timing

The known-good scripted patch adds a first-line comparison before slicing a candidate line window. It was not exposed to the proposer. Five interleaved paired batches used 128 cases per arm per batch (640 per arm); three A/A pairs used 64 cases each. All measured outputs matched the parent baseline.

- A/A mean-difference 95% interval: **−2.79 ms to +3.63 ms**, containing zero.
- Geometric-mean speedup: **1.0106×**, 95% interval **0.9925× to 1.0290×**.
- Mean paired latency difference: **+0.216 ms**, 95% interval **−0.167 ms to +0.598 ms**.
- Frozen rule: **not met**; the point estimate is below 1.05 and the lower interval does not exceed 1.

This is a generated-input microbenchmark of a real VARE function. The per-call clock excludes model generation, subject import, and container startup; session outer wall time is retained in the JSON result. It does not establish an end-to-end rollout or learning-throughput improvement.

The first timing-driver invocation stopped before it emitted a complete report because the protocol lacked a `cases_per_session` key. Its in-memory observations were discarded. The protocol/driver were corrected and the complete A/A plus paired run was rerun; only that full run is analyzed. The incident is retained separately in `engineering_attempts.jsonl`.

## Reproduction

Use the pinned MLX environment and a local snapshot whose directory name is the specified revision. The proposer fails closed if the snapshot directory does not match the revision and disables hub downloads:

```sh
python3.12 scripts/propose_mlsys_edit_format_local_v1.py \
  --model-id mlx-community/Qwen3-4B-Instruct-2507-4bit \
  --revision 50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b \
  --model-path /path/to/local/snapshots/50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b \
  --prompt results/mlsys-edit-format-local-v1/proposals/attempt-01.prompt.txt \
  --output-dir /tmp/vare-proposal-01 --attempt-id attempt-01 --seed 20261101
```

For an already materialized full candidate module, evaluate it without importing candidate code in the parent:

```sh
DOCKER_CONTEXT=colima PYTHONPATH=src python3.12 scripts/evaluate_mlsys_edit_format_local_v1.py \
  --candidate results/mlsys-edit-format-local-v1/proposals/attempt-01.candidate.py \
  --out /tmp/vare-proposal-01-evaluation.json --attempt-id attempt-01
```

Reproduce the scripted-control paired timing after verifying the source hashes:

```sh
DOCKER_CONTEXT=colima PYTHONPATH=src python3.12 scripts/benchmark_mlsys_edit_format_local_v1.py
```

The concise outcome is in [`campaign_summary.json`](../results/mlsys-edit-format-local-v1/campaign_summary.json); detailed timings are in [`control-benchmark.json`](../results/mlsys-edit-format-local-v1/control-benchmark.json), and all retained artifacts are covered by [`SHA256SUMS.txt`](../results/mlsys-edit-format-local-v1/SHA256SUMS.txt).

## Decision and limits

Do not adopt the model patch or claim a speedup from the scripted optimization. The real-model step was completed; the independent verifier rejected both attempts. The control benchmark did not pass its threshold.

A second model target was investigated in the durable trajectory path. The existing single-host benchmark reports **54.53 ± 1.85 vs 36.16 ± 2.68 trajectories/s** for async vs sync, but queue-inclusive p95 latency is **44.04–46.45 s vs 0.240–0.290 s**. It is a real VARE worker/store path with synthetic policy and verifier work ([runtime report](async-trajectory-runtime.md#measured-cpu-result)). This exposes a throughput/latency tradeoff, but not yet a task-specific real-model bottleneck. Tuning admission or persistence without a frozen real-task workload and independent recovery evaluator could merely move queued work or alter hash-chain transaction behavior. I therefore did not spend a third proposer attempt on that target. The boundary is recorded; a real-model proposal on it remains unrun.
