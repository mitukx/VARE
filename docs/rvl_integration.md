# Recursive-Verification-Lag integration

The existing `mitukx/Recursive-Verification-Lag` repository owns the lower-level substrate: async/token-exact rollout, verifier execution, GRPO, durable replay, verification debt, weight publication and GPU experiment harnesses. VARE sits above that stack.

Recommended split:

- **RVL:** rollout/training/verifier execution, immutable behavior data, replay leases, weight sync, distributed/GPU evidence.
- **VARE:** failure discovery, curriculum allocation, current-freshness screening, verifier policy, experiment selection, independent held-out promotion and evidence governance.

## Integration surfaces

1. `RVLTokenReplayReader` opens RVL `TokenReplay` SQLite in read-only mode. It preserves group `policy_version`, `verifier_version`, behavior logprobs, reward provenance and replay status. VARE never rewrites RVL replay rows.
2. `RVLOuterPlanner` converts current replay state into freeze/throttle/verifier-refresh controls and task-family weights. Data outside current freshness bounds can trigger a systems intervention but cannot boost curriculum weight.
3. `RVLGRPOHooks` directly wraps RVL `HFLocalBackend` and `HFCausalLMGRPOTrainer` for transactional candidate updates. It requires token-exact generation metadata and restores the incumbent until VARE's held-out gate accepts the candidate.

Candidate training invalidates the shared runtime's loaded-policy marker before the first in-place update. If `train_step`, candidate snapshotting, or the first incumbent restore raises, the adapter removes the candidate snapshot and attempts to restore the saved incumbent before releasing the model lock. A fake-trainer regression injects an exception after partial policy/optimizer mutation. A second CPU smoke executes one real `HFCausalLMGRPOTrainer.train_step` from pinned upstream commit `c7e646b`, then injects a failure before VARE snapshots or promotes the candidate; model, optimizer, RNG, active identity, and the next incumbent rollout all pass. The [protocol](../protocols/rvl_grpo_partial_failure_v1.json), [validator](../scripts/validate_rvl_grpo_partial_failure.py), and [run bundle](../results/rvl-grpo-partial-failure-v1/run-1/) preserve the scope. If rollback itself fails, the adapter raises an explicit unknown-state error; it does not claim the runtime is safe. These checks do not establish mid-kernel recovery, process/power-loss recovery, or model-learning evidence.

Evaluation task IDs must be unique because paired scores are retained in a task-ID map. The adapter rejects duplicate IDs before generation and verifies that each returned evaluation generation carries the requested task ID and prompt before scoring it. The CPU reproducer shows that the old adapter overwrote one duplicate-ID score and accepted a response bound to a different task; see the [identity contract report](rvl-eval-task-identity-v1.md) and its [reproducer](../reproducers/rvl_grpo_eval_identity_v1.py).

The [evaluation-to-promotion integration regression](rvl-evaluation-promotion-e2e-v1-report.md) now exercises actual `RVLGRPOHooks.evaluate` reports through `CapabilityLoop` and `PromotionGate` to promote/discard. It verifies valid paired promotion, malformed/missing/underreported/mismatched evidence, aggregate-only compatibility, duplicate task IDs, wrong report-policy identity, task-misbound generations, and exact candidate cleanup on both rejection and evaluator exception. A historical-gate control reproduces a false promotion when `n` and the primary aggregate cover two rows but paired metadata retains one. Stop expanding this evaluation infrastructure; it establishes a checked local contract, not evaluator truthfulness or model improvement.

VARE re-screens replay freshness **at training time**. Insertion-time freshness is not trusted after policy or verifier versions advance.

The critical question is whether these adapters preserve trustworthy learning and independent evaluation when used in a post-training experiment. The existing comparison is locked in `protocols/l2_rvl_qwen_v1.lock.json`; it requires a 0.5B model and a three-arm, three-seed run and remains unrun under the current no-spend CPU budget. Do not change that lock or present the hooks as training evidence. For this VARE-specific comparison, the affordable CPU step remains the synthetic preference-policy control in [`post-training-plan.md`](post-training-plan.md), with held-out preference metrics, explicit policy drift, per-seed results, and exact compute reporting. A toy result cannot establish model capability. The separate real-model RVL evidence and corrected follow-up status are recorded below.

## Related real-model RL evidence in RVL

The sibling RVL repository also records a free single-T4 Qwen2.5-0.5B/GSM8K pilot: six conditions and 24 optimizer steps completed, but mean exact accuracy fell from 31.25% to 18.75% on its 16-question evaluation subset. A same-weight rollout/learner probability mismatch was measured before training; the sampler inherited a repetition penalty while the learner scored raw logits. The [full report](https://github.com/mitukx/Recursive-Verification-Lag/blob/main/docs/free_colab_pilot_evidence.md) retains the negative result and its limits. It is not evidence that correctly matched GRPO improved the model.

RVL has since frozen a corrected follow-up protocol with a 32-question evaluation split and a per-update fresh-policy gate. Its [runbook](https://github.com/mitukx/Recursive-Verification-Lag/blob/research/corrected-rlvr-pilot-v2/docs/corrected_rlvr_pilot_v2.md) and [free-runtime notebook](https://github.com/mitukx/Recursive-Verification-Lag/blob/research/corrected-rlvr-pilot-v2/notebooks/free_colab_rlvr_pilot_v2.ipynb) are available on the research branch. The follow-up has not been executed. These are RVL experiments, separate from VARE's adapter rollback smoke and from the unrun `l2_rvl_qwen_v1` comparison; no outcome should be attributed to VARE until the candidate is run through VARE's independent evaluation and promotion path.
